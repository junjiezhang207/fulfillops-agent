# 企业数据与记忆

## 1. 企业数据

当前项目使用演示数据模拟企业订单、库存和知识库。

| 数据 | 用途 |
| --- | --- |
| 订单数据 | 判断订单状态、优先级、客户类型、履约要求 |
| 库存数据 | 判断仓库库存、缺货、可调拨情况 |
| 知识库文档 | 提供制度、规则、SOP 和风险依据 |

企业真实上传数据时，通常不是让用户上传杂乱文件再让模型解析，而是上传已经清洗好的结构化数据，例如 CSV、Excel、数据库同步结果或 API 数据。

## 2. 订单库存和 RAG 的边界

订单、库存属于结构化业务数据，应该走 Repository / Service。

规则、制度、SOP 属于非结构化或半结构化知识，应该进入 RAG。

这个边界能减少幻觉，也方便权限控制和审计。

## 3. 短期记忆

短期记忆负责保存当前会话上下文，服务于多轮对话。

当前策略：

- 优先使用 Redis。
- Redis 不可用时降级到 LangGraph `MemorySaver`。
- 前端也保存当前页面聊天记录，提升演示体验。

如果看到 Redis 搜索命令不支持的日志，说明当前 Redis 不是完整 RediSearch 环境，系统会自动降级。

## 4. 长期记忆

长期记忆用于保存跨会话可复用的信息，例如用户偏好、历史决策摘要、常见问题处理结论。

推荐技术：

```text
MySQL + Milvus
```

原因：

- Windows 本地可以通过 Docker 跑起来。
- MySQL 适合保存结构化元数据、TTL、importance、访问次数和审计记录。
- Milvus 适合保存可重建的语义向量索引，支持相似记忆检索。
- 结构化数据和向量索引拆开，更符合企业电商里 OMS/WMS 数据与向量检索的职责边界。

当前向量维度建议和 Embedding 保持一致：

```env
LONG_TERM_MEMORY_VECTOR_DIMENSION=1024
```

## 5. 什么时候写入长期记忆

不应该每一句话都写长期记忆。更合理的写入条件：

- 用户明确表达长期偏好。
- 一次复杂任务形成了可复用结论。
- 业务规则被人工确认过。
- Agent 多轮推理后生成了稳定决策摘要。
- 会话结束时进行摘要沉淀。

写入长期记忆前应做去重、压缩、敏感信息过滤和来源标记。
